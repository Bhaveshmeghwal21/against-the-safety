# Azure GPT-6 Luna comparison with our RAG adapters

Date: 9 November 2026. This is a team-run evaluation of the Azure deployment, not an official Lexsi leaderboard or a comparison published by the model providers. The analysis and checkpoints are kept inside this workspace.

## Results and interpretation

All 2,069 planned episodes completed in each Azure interface. Across all eight suites there were 2,990 recorded original-format API calls and 5,761 native-tool calls; the native run had three provider-filtered episodes. The final round-5 paired table uses 876 of the original 938 episode keys: three were provider-blocked and 59 more were excluded because at least one compared actor encountered alternate answer evidence under scorer v2. The native Azure actor alone triggered 53 v2 exclusions, against 11 for `main`; the common intersection changes the evaluated population, and these exclusions can bias conclusions.

| System | Round-5 macro success | Supported correct on answerable cases | Unsupported on hidden cases | False refusal on answerable cases |
| --- | ---: | ---: | ---: | ---: |
| `main` + FB + V | 50.7% | 27.6% | 25/315 (7.9%) | 39.0% |
| `candF1` + FB + V | 55.7% | 32.4% | 26/315 (8.3%) | 37.6% |
| Azure native + FB | 54.8% | 39.2% | 62/315 (19.7%) | 2.7% |
| Azure exact + FB | 42.8% | 13.7% | 36/315 (11.4%) | 36.9% |

On this selected common sample, native Azure answers more answerable cases correctly but produces more unsupported answers on hidden-evidence cases. Versus `main` + FB + V, the paired difference in native Azure's unsupported rate is +11.7 percentage points, with a question-level bootstrap 95% interval of +5.9 to +17.6 points. Its macro difference is +4.0 points, interval −0.03 to +8.2 points, so a macro advantage is not established by this test. Against `candF1` + FB + V the macro difference is −0.9 points, interval −5.6 to +3.8; its unsupported rate is +11.4 points, interval +5.7 to +17.3. These intervals do not remove the unequal-verifier, prompting or other setup differences described below.

On the common round-5 sample, **38.2%** of original-format Azure episodes and **24.2%** of native Azure episodes ended invalid before FB. FB makes an invalid result an abstention: that often improves success when evidence is hidden, but it does not show that the model itself deliberately abstained. The raw native macro is 28.7% versus 54.8% after the FB policy; the complete report includes both. Our repaired systems' verifier can also create abstentions and, unlike FB alone, may suppress unsupported answers; its cost in false refusals is visible in the table. There is no evidence here that either adapter has eliminated unsupported answers.

The older suites have different trade-offs: for example, on the common SQuAD 2.0 sample native Azure has 46.6% supported correct versus raw `main`'s 5.5%, but 51/124 unsupported hidden cases versus `main`'s 5/124. On the 2Wiki and MuSiQue samples, native Azure ends invalid on roughly half the episodes before FB. RGB integration is hard for all compared actors. See the [full suite-by-suite table](../reports/azure_round5_comparison.md) for denominators, all systems and the FB rows; these earlier suites have no saved final-system verifier or `candF1` comparison.

Audit of all completed Azure episodes found no blank search observations; one search in each interface returned no retrieved hits. Original-format calls had 59 length finishes across the eight suites; native had none. The native model requested multiple tools in 46 calls, of which the harness executed only the first, as required by its one-search-per-turn interface. The post-run trace audit found no cases requiring the optional plain-text answer/refusal normalization, so the native result differences arise from the native tool interface and model behavior rather than that normalization. We cannot infer how accepting multiple tool calls would have changed the scores.

At a 10,000-episode/month scenario, the native Azure token estimate is **$2.66**, while our submitted model costs about **$6.30** at $0.526/T4-hour if the GPU can be kept perfectly busy and stopped immediately; an always-on 730-hour VM would be **$383.98** before other costs. The measured actor throughput was about 20 output tokens/s when batched; estimated main-system actor plus verifier time was 4.31 amortized GPU seconds per episode. Azure's 938 recorded native round-5 episodes used approximately $0.25 of tokens, and the 8,751 recorded calls across all eight suites and both interfaces total approximately $0.86, at the illustrative rates. These estimates exclude unrecorded pilots or interrupted calls and do not establish the account's actual charge. See the [full ROI assumptions](../reports/azure_roi.md).

## What we compared

Our submitted round-5 system is Cohere Tiny Aya Global with the `main` adapter, a fail-closed rule (FB), and the previously saved self-checking verifier (V). The round-5 alternative `candF1` uses its own actor adapter with the same repairs. We reconstruct their scores from the saved per-episode transcripts and saved verifier verdicts. **No adapter, GPU job, or Kaggle notebook was run for this comparison.**

The closed model is the user's Azure `gpt-6-luna` deployment; successful responses identified themselves as `gpt-6-luna-2026-09-22`. The API key is read at runtime from the process environment or Windows user environment and is not stored in the results. The full raw model responses, usage metadata, episode transcripts, checkpoints, provider blocks and run configurations are in the corresponding subfolders of `runs/azure_round5` and `runs/azure_round5_native`.

There are two independently generated Azure runs:

1. **Original format (`azure_exact`).** The same system prompt, search/action grammar and lenient parser used for Tiny Aya. This measures compatibility with the existing harness, and an invalid output can reflect a format mismatch rather than lack of general ability.
2. **Native tools (`azure_native`).** The same retrieval environment and answer-tag instruction, but the model calls Azure's `search_corpus` function tool. The wrapper maps the first tool call to the harness search and normalizes a plain explicit refusal or an answer with already-supplied citation tags. It does not add citation IDs. The raw response and calls are saved. This is an interface adaptation, so it is not an identical-prompt experiment; the wrapper has simple rule-based limits.

For each benchmark, all systems use the same question and variant keys, corpus/index, masked-evidence conditions, top-three search results, 800-character passage display, and three-search budget. Models generate their own search queries and can see different passages. Tiny Aya's original run used greedy decoding and a 160-token generation cap; Azure uses the deployment's default temperature of 1 and a 512-completion-token cap that includes reasoning. Native tools require `reasoning_effort=none` on this deployment, while original-format Azure uses the default reasoning setting. These are single stochastic Azure runs and cannot isolate the effect of model size from sampling, prompt, interface or inference budget.

FB maps an invalid final/action turn to an abstention. On the adapter systems V also blocks an answer when its saved deterministic checks fail or the saved Tiny Aya checker score is below the threshold. The Azure comparisons include raw and FB results but **no Tiny Aya V**; therefore comparisons of the complete systems are asymmetric. Raw model-to-model rows are included too. FB can make malformed responses look like successful abstentions on hidden-evidence episodes, while causing false refusals on answerable episodes, so report invalid rates and supported-answer success alongside the macro score.

## Benchmarks and scoring

The three final-test suites are `r5t_squad` (385 episodes), `r5t_hotpot` (82), and `r5t_rgb` (471): 938 total episodes before filtering. The round-5 macro averages the success rates on SQuAD single-part, SQuAD compound, HotpotQA, and RGB; a success is a supported correct answer on an answerable case or an abstention on a hidden-evidence case. The score is the project's scorer-v2 metric, not an official dataset leaderboard score. The held-out test had already been opened for the prior round-5 evaluation, so this comparison is not a newly sealed independent test.

Five earlier external suites are also run: 2WikiMultihopQA (166 episodes), MuSiQue (168), SQuAD 2.0 (202), RGB (453), and RGB integration (142). This adds 1,131 episodes, for 2,069 per Azure interface before provider blocks. These are the project's samples and variants, not each benchmark's full official test set. For these earlier suites, saved raw `main` and `candA` results exist, but the final round-5 verifier and `candF1` do not; we cannot claim to compare the complete submitted system or the final alternative on those datasets without rerunning them.

The report uses a single shared episode intersection within each suite or combined round-5 comparison. It drops provider-blocked cases and cases that scorer v2 excludes for any compared system because the supposedly hidden answer appears in a passage it saw. This avoids silently comparing different denominators, but changes the sample relative to the original round-5 report and may select an easier or different subset. Scorer v2's token matching and evidence/alias checks are imperfect; a reported unsupported-answer count is a measurement under this rubric, not proof of absence of hallucinations. Azure content-filter blocks are recorded separately and are not treated as a model abstention or wrong answer. This can introduce selection bias.

Paired 95% bootstrap intervals resample whole question IDs within each dataset, with 3,000 draws and seed 47. They do not account for shared-source-article correlations, repeated model sampling, or benchmark-selection uncertainty. Compare macro, supported-answer rate, unsupported answers among hidden cases, false refusals and invalid outputs together; none is a substitute for the others.

## Cost methodology

The accompanying ROI report applies published Microsoft Global Standard short-context rates to the Azure token usage actually returned by the API. Cache reads and writes are counted separately; completion usage includes reasoning tokens. Local throughput and GPU seconds come from previously saved T4 actor and batched-verifier timings. A 10,000-episode/month scenario compares ideally utilized busy T4 hours at a published East US VM rate to API token cost; the report also gives the cost of a continuously allocated 730-hour VM. This is a scenario, not a bill, performance guarantee, complete development cost, or pricing quote for the user's subscription. It excludes many fixed and ancillary costs, and pilot or interrupted calls may be missing from the recorded usage.

The Tiny Aya model's non-commercial license must be considered before deployment; the cost scenario does not imply commercial rights. ## Reproduction

From PowerShell in the workspace, dot-source `scripts/env.ps1` to keep caches and temporary files inside the workspace. Set `AZURE_OPENAI_API_KEY` and set `AZURE_OPENAI_CHAT_URL` to the Azure deployment's HTTPS chat-completions URL. Then `python scripts/azure_rag_eval.py --mode exact --out runs/azure_round5` and `python scripts/azure_rag_eval.py --mode native --out runs/azure_round5_native` resume their own checkpoints. These commands send new prompts to Azure and can incur charges if results are missing. For offline reporting, set `HF_HUB_OFFLINE=1`, then run `python scripts/report_azure_compare.py` and `python scripts/report_azure_roi.py`.

Result files: [paired comparison](../reports/azure_round5_comparison.md), [machine-readable comparison](../reports/azure_round5_comparison.json), [cost analysis](../reports/azure_roi.md), and [machine-readable cost data](../reports/azure_roi.json).
